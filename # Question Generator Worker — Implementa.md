# Question Generator Worker — Implementation Plan

Python worker that consumes question-generation jobs from **AWS SQS** (published by the existing Node.js API), runs a **LangGraph** pipeline (extract → embed → select → generate → judge → regenerate loop), persists results + rejection reasons, and reports status for polling.

No web framework. Single long-running asyncio process.

## 4. Job Payload (SQS message body, JSON)

```python
class JobPayload(BaseModel):
    job_id: str                    # idempotency key, generated by Node API
    s3_key: str                    # uploaded PDF location
    num_questions: int = Field(ge=1, le=50)
    difficulty: Literal["easy", "medium", "hard"]
    topic: str | None = None
    question_type: str | None = None   # optional future: mcq / short / etc.
    requested_at: datetime
```

Validation failure (malformed JSON / schema error) → mark job `failed` in DB with reason, **delete the message** (retrying can't fix a bad payload), log at error level.

## 5. SQS Consumer

**Loop (sqs_consumer.py):**
1. `receive_message` with long polling (`WaitTimeSeconds=20`), `MaxNumberOfMessages`, and `AttributeNames=['ApproximateReceiveCount']`.
2. For each message, acquire `asyncio.Semaphore(WORKER_CONCURRENCY)`, spawn a task.
3. Per task:
   - Start a **visibility heartbeat**: background task calling `change_message_visibility` every `VISIBILITY_HEARTBEAT_INTERVAL` seconds while the pipeline runs (pipeline can take minutes; without this SQS redelivers mid-run).
   - Run dispatcher → pipeline.
   - **Success** → `delete_message` (ack only after results are persisted).
   - **Transient failure** (LLM outage, S3 error after retries) → do NOT delete; stop heartbeat; message becomes visible again and SQS redelivers. `maxReceiveCount` on the queue's redrive policy (set to e.g. 4) moves poison messages to the DLQ automatically.
   - **Permanent failure** (corrupt PDF, doc too short, bad payload) → write `failed` status + reason to DB, then `delete_message` — no pointless retries.
4. Classify errors: define `PermanentJobError` / `TransientJobError` exception types; nodes raise the right one.

**Graceful shutdown (main.py):**
- Trap SIGTERM/SIGINT → set shutdown flag → stop polling → `await` in-flight tasks (with a deadline, e.g. 5 min) → exit. Unfinished jobs: stop heartbeat so SQS redelivers.

**Idempotency (validate node):**
- On job start: `INSERT ... ON CONFLICT (job_id)` a status row. If a row already exists with status `completed`, skip pipeline and delete message. If `in_progress` with a recent heartbeat timestamp, another worker owns it → don't delete, just release (defensive; visibility timeout normally prevents this).

## 6. LangGraph State Schema

```python
class RejectedQuestion(BaseModel):
    text: str
    reason: str                    # from judge or dedupe
    source: Literal["judge", "dedupe"]

class GeneratedQuestion(BaseModel):
    text: str
    answer: str
    difficulty: str
    source_chunk_ids: list[int]

class PipelineState(TypedDict):
    job: JobPayload
    pdf_bytes: bytes | None
    raw_text: str | None
    chunks: list[str]
    chunk_embeddings: list[list[float]]
    selected_chunk_ids: list[int]
    accepted: Annotated[list[GeneratedQuestion], operator.add]
    rejected: Annotated[list[RejectedQuestion], operator.add]
    regeneration_round: int
    needed: int                    # questions still missing
    error: str | None
```

## 7. Nodes & Edges

```
validate ─→ fetch_pdf ─→ extract ─→ chunk_embed ─→ select_chunks ─→ generate ─→ dedupe ─→ judge ─┬─→ persist ─→ END
                                                                        ▲                        │
                                                                        └──── (needed > 0 and ───┘
                                                                              round < MAX_ROUNDS)
```

Each node's first action: `status.update(job_id, stage=<node_name>)` — this is what the Node API's polling endpoint reads.

**validate** — payload sanity + idempotency (above).

**fetch_pdf** — S3 `get_object`, tenacity retry (3 attempts, exponential backoff + jitter). Enforce ≤10MB defensively even though upload already limits it.

**extract** — pymupdf text extraction.
- `len(text) < MIN_EXTRACTED_CHARS` → `PermanentJobError("PDF appears scanned or empty — no extractable text")`.
- `len(text) < num_questions * MIN_CHARS_PER_QUESTION` → either fail with "document too short for N questions" or clamp `num_questions` down and record a warning in state (pick one behavior; recommend clamp + warning surfaced to user).

**chunk_embed** — `RecursiveCharacterTextSplitter` (~800–1000 chars, 100–150 overlap). Batch-embed all chunks (single API call where possible). Embeddings kept in state; also embed the topic string here if present.

**select_chunks** —
- Topic present: cosine similarity(topic, each chunk), take top-k where `k = min(len(chunks), max(num_questions, num_questions * 2))` — give the generator ~2 chunks per question when available.
- No topic: **spread selection** — evenly strided indices across the document (or k-means over embeddings, one chunk per cluster) so questions cover the whole PDF, not just page 1.
- Fewer chunks than questions: use all chunks; generator prompt instructs multiple questions per chunk.

**generate** — chat model `.with_structured_output(list[GeneratedQuestion])`.
- Prompt inputs: selected chunk texts (with ids), difficulty definition (spell out what easy/medium/hard means — don't just say the word), topic, count = `state["needed"]`.
- On regeneration rounds: include `rejected` questions verbatim with instruction "do not repeat or rephrase these."
- Ask for `needed + 2` questions (overshoot) so dedupe/judge attrition doesn't force an extra round.

**dedupe** — embed the candidate questions, pairwise cosine within the batch AND against already-`accepted` questions. Any candidate ≥ threshold → move to `rejected` with `source="dedupe"`, reason "near-duplicate of: <other question>".

**judge** — separate (can be cheaper) model, `.with_structured_output`:

```python
class JudgeVerdict(BaseModel):
    question_index: int
    difficulty_match: bool
    topic_relevant: bool          # true when no topic given
    grounded_in_source: bool      # answerable from the provided chunks
    accept: bool
    reason: str                   # REQUIRED — this is the "why rejected" record
```

Judge sees: questions + the chunks they cite + difficulty definition + topic. Accepted → `accepted`; rejected → `rejected` with judge reason. Then set `needed = num_questions - len(accepted)`.

**Conditional edge after judge:**
- `needed <= 0` → persist.
- `needed > 0 and regeneration_round < MAX_REGENERATION_ROUNDS` → increment round → generate.
- Rounds exhausted with a shortfall → persist what we have, status `completed_partial`, include shortfall reason (e.g. "document supported only 7 unique hard questions").

**persist** — single transaction: upsert questions, insert rejected list (question text + reason + source + round), set final status. Only after this commits does the consumer delete the SQS message.

## 8. Retry Layers (outermost → innermost)

1. **SQS redelivery + DLQ** — crash/transient safety net (redrive `maxReceiveCount=4`).
2. **LangGraph `retry_policy`** per node — e.g. `RetryPolicy(max_attempts=3)` on fetch_pdf, chunk_embed, generate, judge; retry only on `TransientJobError`/network exceptions.
3. **tenacity** inside services (S3, DB) — exponential backoff + jitter.
4. **Model client `max_retries`** — rate-limit/5xx handling at the SDK level.

Never retry `PermanentJobError` at any layer.

## 9. Status Model (DB table `generation_jobs`)

```
job_id (PK) | status | stage | progress_meta (jsonb) | error_reason |
attempt_count | created_at | updated_at
```

`status`: `queued → in_progress → completed | completed_partial | failed`
`stage`: current node name (drives the polling UI).
Rejected questions in a child table so the UI can show "10 generated, 3 rejected: <reasons>".

## 10. Observability

- structlog JSON logs; bind `job_id` once, every line carries it.
- Log per node: duration, token usage (from LLM response metadata), counts (chunks, candidates, accepted, rejected).
- Counters worth tracking from day one: jobs completed/failed/partial, avg regeneration rounds, rejection reasons histogram — the last one tells you how to improve the generator prompt.

## 11. Testing Plan

- **Unit per node**, LLM/embeddings mocked: extract (normal/tiny/scanned/corrupt fixtures), select_chunks (topic vs no-topic, fewer-chunks-than-questions), dedupe (crafted near-duplicates), judge routing (verdict → edge decision), regeneration cap.
- **Graph-level**: run full graph with fake LLM returning scripted outputs; assert final state for: all accepted first round; partial acceptance → 1 regen round; rounds exhausted → `completed_partial`.
- **Consumer**: LocalStack (or moto) for SQS — ack-on-success, no-ack-on-transient-failure, delete-on-permanent-failure, heartbeat extends visibility, SIGTERM drains in-flight job.

## 12. Deployment Notes

- Dockerize; run N replicas (ECS service / EC2 / your self-hosted box). Scale on `ApproximateNumberOfMessagesVisible`.
- Health: liveness = process up + last-poll timestamp file/heartbeat; no HTTP server needed (or a 5-line aiohttp `/healthz` if the orchestrator demands one).
- IAM: worker role needs `sqs:ReceiveMessage/DeleteMessage/ChangeMessageVisibility` on the queue, `s3:GetObject` on the bucket. Nothing more.
